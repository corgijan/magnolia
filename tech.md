# Magnolia — IDEA.md > Version-accurate, immutable SBOM archive for CRA compliance. ## 1. Problem Der EU Cyber Resilience Act (CRA) verpflichtet Hersteller, für den gesamten Support-Zeitraum eines Produkts nachweisen zu können, **welche Software-Stückliste (SBOM) zu welcher ausgelieferten Version gehörte**. Bestehende Tools lösen das nur halb: | Tool | Stärke | Lücke | |---|---|---| | Dependency-Track | Live-Vulnerability-Analyse, Policies, Risk-Scoring | kein revisionssicheres Langzeitarchiv, "latest state"-orientiert | | Git / Artifact-Registry | Versionierung | keine Unveränderlichkeit, keine Signatur-Kette, keine Retention-Policy | | S3 allein | billig, dauerhaft | keine Auth-Semantik, keine Manifest-/Integritätslogik, kein Audit-Workflow | **Magnolia schließt genau diese Lücke: das Compliance-Archiv neben dem Analyse-Tool.** Dependency-Track macht "was ist heute verwundbar?", Magnolia macht "was genau haben wir am Tag X ausgeliefert — und beweise es". ## 2. Kernidee Ein **append-only, kryptografisch verkettetes und signiertes SBOM-Archiv** auf S3-Basis, das eher wie ein Transparency Log (Certificate Transparency / Rekor) funktioniert als wie ein Dateiablage-Dienst. Leitprinzipien: 1. **Immutable by default** — S3 Object Lock (Governance oder Compliance Mode), die Anwendung braucht nie Delete-Rechte auf gelockte Objekte. 2. **Append-only statt Update** — Republish einer Version erzeugt eine neue Revision; alte Revisionen bleiben dauerhaft abrufbar. 3. **Tamper-evident** — jedes Manifest referenziert `previous_manifest_sha256` (Hash-Kette). Einfügen, Löschen oder Umsortieren von Historie ist auch mit Storage-Zugriff erkennbar. 4. **Notarisierung durch das System** — Magnolia gegensigniert beim Ingest mit einem domänen-spezifischen Schlüssel; der private Key verlässt nie den Signer-Backend (Vault/KMS/HSM). 5. **Vendor-agnostisch** — `Signer`- und `ObjectStore`-Traits; austauschbar zwischen Vault Transit, AWS/GCP/Azure KMS, PKCS#11-HSM bzw. S3/MinIO. 6. **S3 ist Source of Truth, Postgres nur Query-Index** — der Index muss aus S3 vollständig rekonstruierbar sein (Rebuild-Job = DR-Story + Integritätscheck). 7. **Separation of Duties** — Uploader liefern SBOMs, Auditoren kommentieren und attestieren, aber niemand kann beides. ## 3. Adressierung & Mandantenfähigkeit Docker-artiges Schema, Domain als Mandantengrenze: ``` domain/namespace/.../product:version acme-corp/product1/subprod1/widget-firmware:2.4.1 ``` * Namespaces sind freie Strings, mit `/` hierarchisch wie Linux-Ordner. * Ein Grant auf `/product1` deckt alle Unterpfade ab; ein Grant auf `/product1/subprod1` nur diesen Teilbaum. * **Domain = Tenant.** Auth, Quotas, Retention-Floor und **Signaturschlüssel** sind pro Domain gescoped → kryptografische, nicht nur logische Isolation. ## 4. Unveränderliche Audit-Annotationen Ein signiertes Manifest lässt sich nicht mehr ändern — Auditor-Notizen werden daher **eigene, separat signierte und verkettete Records**, die auf ein Manifest verweisen. Ergebnis: zwei parallele Append-Only-Ketten pro Version: 1. **Manifest-Kette** (Uploader-getrieben) — SBOM-Revisionen 2. **Annotation-Kette** (Auditor-getrieben) — Findings, Risikoakzeptanzen, Refs Keine Kette kann die andere überschreiben. Die vollständige Historie bleibt erhalten und ist verifizierbar. ## 5. Rollenmodell ``` super_admin → plattformweit: Domains anlegen, Notfallzugriff (mit Pflicht-Reason) domain_admin → Keys & ACLs innerhalb einer Domain uploader → SBOM-Upload in gewährten Namespaces (keine Annotationen) auditor → Lesen + Annotationen erstellen (kein SBOM-Upload) ``` Authentifizierung ausschließlich über **API-Keys** (gehasht at rest, einmalig bei Erstellung sichtbar, `Authorization: Bearer <key>`). ## 6. Manifest-Schema (v1.0) ```json { "manifest_version": "1.0", "domain": "acme-corp", "namespace": "product1/subprod1", "product": "widget-firmware", "version": "2.4.1", "revision": 3, "created_at": "2025-06-01T12:00:00Z", "uploader_key_id": "ak_9f2...", "sbom_object": { "path": "sbom.json.gz", "sha256_canonical_uncompressed": "8f3a...", "format": "cyclonedx-1.5" }, "previous_manifest_sha256": "...", "retention": { "mode": "compliance", "retention_until": "2032-06-01T00:00:00Z", "post_expiry_action": "manual_review" }, "signature": { "alg": "ECDSA_SHA_256", "signer_backend": "vault-transit", "key_id": "domain-acme-corp-key-v2", "value": "base64..." } } ``` **Hashing-Regel:** SHA-256 immer über das **kanonisierte, unkomprimierte** SBOM (JSON Canonicalization / RFC 8785), nie über das komprimierte Artefakt — sonst bricht die Verifikation, sobald sich Kompressionsverfahren oder -level ändern. ## 7. Retention-Regeln * Retention pro Version konfigurierbar, aber **nur verlängerbar, nie verkürzbar**. * **Minimum-Retention-Floor** pro Domain/Namespace konfigurierbar (z. B. "nichts unter 5 Jahre"). * Object-Lock-Modus (governance/compliance) explizit pro Namespace wählbar, niemals stillschweigender Default. * **Post-Expiry-Action** konfigurierbar: `auto_delete` (Lifecycle Rule) oder `manual_review` (Hold bis manuelle Freigabe). ## 8. Tech-Stack | Bereich | Wahl | |---|---| | Sprache | Rust | | HTTP | `axum` + `tower` | | DB | Postgres via `sqlx` (compile-time checked) | | Storage | `aws-sdk-s3` (S3 / MinIO) hinter `ObjectStore`-Trait | | Signing | `Signer`-Trait → `vaultrs`, `aws-sdk-kms`, `pkcs11` | | Hashing | `sha2`, Key-Hashing `argon2` | | Frontend | statisches Vanilla-JS (`fetch`), kein Build-Step | | Observability | `tracing` + OpenTelemetry | ## 9. Bewusst out of scope für v1 * Dependency-Track-Integration (Push/Pull) — später * Client-seitige Uploader-Signaturen — v1: Magnolia ist alleiniger Notar * SSO / OIDC / Human-Login — v1: nur API-Keys * SBOM-Diffing, Vulnerability-Matching, Policy-Engine — das macht dtrack ## 10. Nicht-Ziele Magnolia ist **kein** Scanner, **kein** Vulnerability-Management und **kein** Ersatz für Dependency-Track. Es ist ein revisionssicherer Tresor mit Auditor-Workflow — bewusst klein im Funktionsumfang, aber kompromisslos bei Integrität und Nachweisbarkeit.
